# Michi-Neko — Senior Build Assessment (SBA)

**Date:** 2026-09-27 03:12:51
**Scope:** `index.html` + all 29 modules in `src/` (687 KB)
**Lens:** Mobile-browser-first. Fast boot, smooth frame pacing, high visual density, low friction.
**Out of scope:** `cadJS/`, `dawCAT/`, `OLD/`, `data/`, `tools/`, and `cad_overrides.js` (authoring dependency — runtime hook noted, not reviewed).

---

## 0. Verdict

Michi-Neko is a **genuinely well-engineered, feature-complete game** that is architecturally a year ahead of where most browser-first hobby projects sit. The rendering pipeline, the adaptive-quality governor, the save system, and the context-loss handling are all production-grade.

The problem is not the code. The problem is that **almost all of that engineering is aimed at the desktop high tier**, and the mobile path is a set of afterthought subtraction rules layered on top. On a modern phone the game will *run* — the WebGL2 gate, the auto-tier, the eco governor and the half-res bloom all work — but it will open slowly, drop frames in the first ten seconds while shaders compile, and then quietly give up quality permanently because of three specific bugs (§1) that trigger on every mobile boot.

**Overall: the game is shippable and the foundation is excellent. The mobile first-run experience is not yet finished.**

| Area | Grade | Note |
|---|---|---|
| Rendering architecture | A | Tier-driven MSAA, half-res bloom, fused output pass, depth-attached RTs |
| Adaptive performance | A− | Two-stage ladder + eco governor + startup probe. Sound design, two real bugs |
| Save / persistence | A | Versioned, validated, backed up, exportable, pagehide-safe |
| Mobile boot & first-run | **C** | ~1.7 MB unminified JS over CDN, no offline, no pre-compiled boot frame |
| Mobile controls | B− | Correct and safe-area aware, but rigid, no prowl, no pause button |
| Mobile sustained performance | **C+** | Never measured on real hardware; 20-min session unverified |
| Visual density / detail | A− | Best-in-class for procedural. Foliage + weather + sky is genuinely lovely |
| Accessibility | D | Effectively none. Blocks pinch-zoom, no reduced-motion in 3D, no text scaling |
| Content depth | B | Deep Kyoto *valley*, but one map; 3 NPCs; no ending beat that lands |

## 1. Critical — bugs that hurt every mobile session

### 1.1 The startup probe permanently downgrades quality on mobile, forever

`main.js:1335-1359` (`updateStartupProbe`) samples title-screen FPS and, if the median is under 34, writes a **lower quality tier into the persistent settings**:

```js
const target = q === 'high' ? 'medium' : 'low';
this.settings.set('quality', target);   // <-- persists to localStorage
this.applyQuality();
try { localStorage.setItem('catwalk_probe_v1', ...); } catch (e) {}
```

Three compounding problems:

1. **The probe cache is written but never read.** Verified across all of `src/`: **1** `setItem('catwalk_probe_v1')`, **0** `getItem`. The "cached per game version" comment on line 1331 describes intent, not behaviour. The probe re-runs on *every page load*, forever.

2. **It writes a permanent, user-invisible downgrade.** `settings.set()` persists to `catwalk_settings_v1` (`settings.js:30`). The player never chose this. The Settings screen will then show "Low" — and because the probe re-fires on the next load while `resolveQuality()` no longer returns `'auto'`, the target recomputes to `'low'` and the tier is now **pinned**. The device can never climb back.

3. **The measurement is not representative.** The probe samples the *title screen*, which `updateFrameGovernor` (`main.js:1666-1669`) **deliberately caps at 30 fps on touch devices**:

```js
if (this.menu.mode === 'title' && this.isTouchDevice()) {
  this.frameFloor = 1 / 30;
}
```

So on mobile the probe measures a self-imposed 30 fps cap, sees a median below 34, and concludes the device is slow. **It is grading the governor's own throttle.** A perfectly capable iPhone is demoted on first launch and stays demoted.

**Fix:** make the cache actually load; measure the first ~8 s of *gameplay* rather than the capped title; never write a downgrade the player did not choose — store it in `catwalk_probe_v1` as an *initial* tier hint that `resolveQuality()` consults only while `quality === 'auto'`.

### 1.2 `applyQuality()` runs on every single user gesture

`installAudioEnableButton` (`main.js:788-805`) binds the audio unlock to **five** window-level capture-phase listeners: `pointerdown`, `pointerup`, `touchend`, `click`, `keydown`. That handler calls `unlockAudioFromGesture` (`main.js:808-820`) → `this.applySettings()` → `this.applyQuality()`.

`applyQuality()` (`main.js:627-726`) is not a cheap idempotent setter. Per gesture it can:

- rebuild the composer's ping-pong render targets and dispose the old pair (`main.js:653-672`),
- dispose and null the sun's shadow map (`main.js:677-683`),
- call `applySmallPropShadows()` → **`this.scene.traverse()` over the entire scene graph** (`main.js:744-758`),
- call `onResize()` → `composer.setSize()` + `bloom.setSize()`,
- rebuild the lantern light pool (`ensureLanternPool`),
- re-apply vegetation density, particle budget, and foliage detail.

On a phone, **every tap on the joystick, JUMP, ACT, meow, or any menu** fires `pointerdown` + `pointerup` + `touchend` + `click` — four gesture events, four full `applyQuality()` passes, each with a full-scene traversal. That is a guaranteed micro-stutter on every touch interaction, and it is precisely the wrong thing to do on the device class the game is supposed to serve.

**Fix:** guard the unlock path so it runs at most once per session — it only needs to run until the context is actually running. `ui.js:85-88` already acknowledges this concern for the HUD scroll, but not for `applyQuality`.

### 1.3 The frame governor and the adaptive ladder can fight each other

`updateFrameGovernor` (`main.js:1660-1686`) and `updateAdaptiveResolution` (`main.js:514-568`) both read `this.ui.fps` and both act on it, on independent 2-second timers, with no shared state and no ordering guarantee.

The failure mode: the governor sets `frameFloor = 1/30` under sustained low FPS. `frameFloor` makes `loop()` **skip simulation and render entirely** on dropped frames (`main.js:1695-1699`). But `ui.fps` is computed inside `ui.update()`, called from `Game.update()` — which is **inside the skipped block**. So while the frame floor is engaged, `ui.fps` stops refreshing and holds a stale value. The adaptive ladder then reads that stale number and cannot evaluate whether the floor helped. Both systems are reasoning about a value that stopped updating the moment it became load-bearing.

**Fix:** sample FPS in `loop()` from raw frame timings, outside the skip block, so the measurement survives frame skipping.

## 2. Serious — first-run and load experience

### 2.1 ~1.7 MB of unminified JavaScript, all blocking, over a CDN

| Item | Size |
|---|---|
| `src/` (29 modules, no minification, no bundling) | **687 KB** |
| `three.module.js` 0.160.0 from unpkg | ~600 KB |
| `docs/images/title-screen.jpg` (boot image) | **374 KB** |
| `index.html` (with ~550 lines of inline CSS) | 34 KB |
| **Cold-load total** | **~1.7 MB across ~31 requests** |

Every module is a separate `import` with a `?v=` query string, and `countryside.js` alone is 153 KB. On a mid-tier Android phone on 4G this is a **multi-second blank screen** behind the boot image — and the boot image is itself a 374 KB JPEG that must download before the spinner means anything.

`AGENTS.md` describes the static server as the delivery mechanism and the README points at GitHub Pages. **There is no compression story, no bundling, no `Content-Encoding` guarantee, and no service worker.** A returning player re-downloads or revalidates the lot.

**Fix, in priority order:**

1. Ship a **service worker** precaching `src/`, `three`, and the boot image. This alone converts every repeat visit from ~1.7 MB to ~0 KB.
2. **Self-host three.js** instead of unpkg. Removes a third-party runtime dependency, a DNS+TLS round trip, and a hard failure mode when unpkg is down or blocked. (The `VERIFICATION_REPORT` already lists "CDN-failure path unmeasured" as open.)
3. Convert the boot image to **WebP** (374 KB → ~50 KB expected). It is `filter: blur(12px)` and `scale(1.08)` — compression artefacts are invisible.
4. Consider deferring `interior.js` (21 KB), `audio.js` (25 KB) and `context_actions.js` (32 KB) behind a dynamic `import()` that resolves during the boot screen. ~80 KB off the critical path.

### 2.2 No offline, and no failure path if the CDN is unreachable

`index.html:553-560` hard-codes the import map to `unpkg.com`. There is no `<script>` fallback, no error banner, and no `window.addEventListener('error')` guard. If unpkg is down, blocked, or throttled, the player gets a **permanently frozen boot screen** with an eternally spinning loader and no message. For a free, no-install, link-shared game, this is the most likely first-run failure.

**Fix:** self-host three.js (§2.1.2) and add a `window.addEventListener('error')` handler that swaps the boot spinner for the existing `#gl-recovery` overlay with an honest message.

### 2.3 Shader compilation is a guaranteed first-frame stall

The startup probe waits 4 seconds before sampling (`main.js:1342`) precisely because "shader compilation dominates frame time there" — the comment acknowledges the problem but the game **never fixes it**. On mobile, where `KHR_parallel_shader_compile` support and driver shader caches are weakest, the first seconds of play are the worst frame pacing the player will ever experience — and they happen exactly while the player is deciding whether they like the game.

**Fix:** call `renderer.compile(scene, camera)` during the boot screen, before the first `composer.render()`, holding the boot image until it resolves. This moves the cost into the loading screen where it belongs.

## 3. Mobile controls — solid foundation, incomplete

### What works well

- Safe-area insets are respected throughout (`index.html:201-241`), including the portrait reflow that repositions MEOW/ACT/JUMP into a left-anchored row.
- `touch-action: none` on `html`, `body` and `canvas` (`index.html:11-12`) stops scroll/zoom interference correctly.
- The floating joystick with a 0.12 deadzone and smoothstep response (`controls.js:224-234`) feels right and is frame-rate independent.
- Joystick and camera-look are cleanly separated by element, so multi-touch move + look works.
- `backdrop-filter` is correctly gated to `pointer: fine` only (`index.html:258-260`) — a genuinely good mobile catch.

### Problems

**3.1 — Prowl has no touch binding.** `KeyC` toggles prowl (`controls.js:57-60`). On mobile there is no equivalent. Prowl is one of the five verbs in the game's identity ("the cat chooses its own pace") and it is simply unreachable on a phone. The touch row has JUMP / ACT / MEOW and no slot for it. **Highest-value single mobile control addition.**

**3.2 — Prowl is not a HUD state either.** The HUD `#mode` line is hard-coded desktop text (`index.html:602`: "WASD + Space, E: Act, M: Meow, C: Prowl"), and `ui.setMode()` is called with the literal strings `'mobile'` / `'desktop'` (`controls.js:23-24`). On mobile that line therefore reads **"mobile"** — not a control hint, a leaked enum value. The player gets no indication that prowl exists, in any form.

**3.3 — The double-tap "careful pace" toggle is undiscoverable and easy to trigger by accident.** `controls.js:146-153` treats two zone `touchstart`s within 320 ms as a mode toggle. A player adjusting their thumb mid-stride will hit this and silently drop to 55 % speed. The only feedback is a toast that appears *after* the fact.

**3.4 — Camera sensitivity is coupled to device.** `sensitivity` maps straight to radians-per-CSS-pixel (`main.js:618`). Phones have roughly 3× the pixel density of desktops, so the same setting produces a very different feel. The 1.7× touch multiplier (`controls.js:118`) is a global fudge that does not adapt to screen size or DPI.

**3.5 — No pause button on mobile.** Pause is `Escape` only (`menus.js:32-37`). On a phone the player **cannot pause, open settings, or save and quit.** Autosave on `pagehide` makes this survivable, but settings are unreachable on mobile at all — quality, volumes, hint mode, and HUD mode are all effectively desktop-keyboard-gated. This is a real functional gap, not a polish item.

## 4. Sustained performance — the honest picture

To be direct: **there are no real-device measurements.** `VERIFICATION_REPORT_2026-09-11.md` is explicit that all testing ran under headless SwiftShader at 2–5 fps, with time-dependent tests stepped manually. Its own budget table is labelled "targets, pending device validation." Nothing in the repo has ever measured this game on a phone.

That matters, because the entire quality strategy rests on assumptions headless testing cannot exercise — thermal throttling, tile-based GPU behaviour, memory pressure, and shader compile cost.

### Risks visible from the code

**4.1 — Auto-tier is pessimistic for modern phones.** `resolveQuality()` (`settings.js:36-46`) maps *every* mobile device with ≥6 cores to `medium`. `medium` means DPR cap 1.25, **2048² shadow map, AO enabled at 8 samples, bloom enabled**, and 0.75 vegetation density. On a Snapdragon 8-series or A17 device that is a lot of work for something that would run comfortably at `high`. Meanwhile a low-core device gets `low` — DPR 1.0, 1024² shadows, no AO, no bloom. The three tiers are far apart with nothing in between.

**4.2 — The `low` tier is a cliff, not a slope.** Dropping to `low` removes AO, bloom *and* light shafts simultaneously. A device that could have run at medium-minus-bloom instead gets a flat, unlit-looking image. The stage-1 adaptive state (`main.js:586-594`) does something smarter (drop shafts, quarter the bloom) — the static tier should borrow from that.

**4.3 — Lantern `PointLight`s are the classic tile-GPU killer.** Up to 4 point lights (`main.js:721`) plus 2 interior lights. `ensureLanternPool()` (`countryside.js:3207-3235`) is commendably honest about this — it sizes the pool rather than dimming to it, which is correct. But the ceiling is still 4 dynamic point lights in the fragment shader on a device that may have a very different per-light cost profile.

**4.4 — `PCFSoftShadowMap` on mobile.** `main.js:69` sets this unconditionally. It is the most expensive of the three three.js shadow filters (16+ taps vs 4 for `BasicShadowMap`). On a low tier with a 1024² map this is still real fill cost. **`PCFShadowMap` should be the low-tier filter.**

**4.5 — `chunkSceneInstances` runs once, at boot, over the whole scene** (`main.js:124`). It measured a 2.2 M-triangle win, which is excellent work. But it is a **one-shot** — chunks are never re-balanced, never LOD-swapped, never unloaded as the player walks the valley. Given the design brief ("don't expand the map early"), a single well-chunked valley is defensible. But a 20-minute session is unverified, and the report itself flags "20-min long sessions: not run."

**4.6 — `ambient_life.js` has no tier lever at all.** Confirmed by the project's own checklist (`BUILD_GUIDE` P1.3, marked partial) and by `VERIFICATION_REPORT` ("Partial"). On the tier that most needs help, butterflies, birds, koi and insects all run at full population. Given butterflies and koi are individually animated meshes, this is a meaningful and entirely avoidable cost.

**4.7 — No memory ceiling.** 723 geometries / 103 textures at last measurement. Nothing prunes, nothing streams, nothing unloads. On a 4 GB Android device running a browser tab alongside a chat app, this is the profile that triggers exactly the `webglcontextlost` the game already handles well (§6) — the recovery path is good, but preventing the loss is better.

## 5. Accessibility — the weakest area, and a values mismatch

This is where the gap between the code and the stated intent is widest. The game's premise is *calm, no-fail, no-pressure*. Its own build guide lists U2.x as the main remaining gap. The code agrees.

**5.1 — Zoom is blocked.** `index.html:5`:

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no">
```

`user-scalable=no` + `maximum-scale=1.0` prevents pinch-zoom for every player — a WCAG 1.4.4 failure. For a game about unhurried looking, telling low-vision players they may not zoom the thing they are looking at is particularly tonally wrong. iOS has ignored `user-scalable=no` since iOS 10, so this is *also* inconsistent behaviour across platforms.

**5.2 — `prefers-reduced-motion` is honoured for CSS, ignored for 3D.** The media query exists and correctly covers the scroll HUD and boot spinner (`index.html:80-86`, `548-551`). But the game has a continuously orbiting title camera (`main.js:1253-1266`), an orbiting rest cinematic (`main.js:1235-1250`), bobbing waypoint markers driven by a generated keyframe animation (`waypoints.js:32-33`), swaying foliage, falling rain/snow/petals, and drifting motes. A player who has asked their OS for reduced motion gets none of it in the 3D layer — which is where nearly all the motion lives. This is item U2.5 and the single most impactful accessibility item on the list.

**5.3 — No text scaling anywhere.** All UI is fixed `px` with `clamp()` on a few touch targets. No UI-scale setting, no font-size control, no rem-based layout. The dialogue box is 14 px fixed (`dialogue.js:30`) built with inline styles, so it is not even reachable from the stylesheet.

**5.4 — No screen-reader path for the core loop.** The game is fundamentally visual. The journal (`main.js:1400-1418`) is `innerHTML` with no `aria-live`; toasts have no live region; dialogue is a bare `document.createElement('div')` with inline styles and no `role`. The boot screen has `role="status"` — the one place it's right. For a game about a cat wandering a valley, a text-mode "here's what you can see and do" fallback would be genuinely achievable and is not attempted.

**5.5 — Information is carried by colour alone in places.** Inventory badges toggle `.active` and change text (`ui.js:129-134`) — that part is fine, they read `🔑 Key ✓` vs `🔑 Key: 0`. But the XP bar, quest fill, and keepsake badges elsewhere rely on colour + width with no shape/icon differentiation (U2.4).

## 6. What is genuinely excellent

Credit where it is due. This is a lot of good work and it should not be lost in a list of gaps.

**The render pipeline is best-in-class for procedural work.**

- Tier-driven MSAA (0/0/4) with `antialias: false` on the default framebuffer.
- Bloom at half resolution, quartered again at adaptive stage 1.
- `OutputPass` + `GradeShader` fused into one fullscreen pass (`GradeOutputShader`).
- Depth-textured ping-pong targets, each with its **own** depth attachment, with a comment explaining exactly why sharing one causes a framebuffer feedback loop and a black screen. That is the kind of comment that saves someone a day.

**The adaptive performance design is genuinely thoughtful.** Two-stage degradation (post-FX first, resolution second), with the explicit rule that resolution is restored *before* the stage walks back so the two never fight (`setPerfStage`, `main.js:577-596`). Hysteresis on recovery. A startup calibration probe. An eco/thermal frame floor. A title-screen perf mode. Setting aside the two bugs in §1, this is a well-reasoned system.

**The save system is better than most shipped games.** Schema versioning with migration (`save.js:35-52`), primary + backup key rotation so a failed write can never destroy the only copy (`save.js:54-69`), validation on read that treats malformed positions as corrupt precisely because "positions are the one field a NaN would soft-lock the game with" (`save.js:16-26`), and autosave on both `pagehide` and `visibilitychange` because "mobile browsers close tabs without a reliable unload event." All four are correct, and all four are commented with *why*.

**`instanced_chunks.js` is a model piece of engineering.** The insight — that three.js culls an `InstancedMesh` as a single unit against the bounding sphere of *all* its instances, so a 40 m forest ring is submitted from anywhere in the valley — is correctly diagnosed, correctly measured (2.2 M triangles), and correctly fixed, including the subtle detail of sharing `BufferAttribute` objects so the base mesh uploads exactly once regardless of chunk count.

**Context-loss handling is right.** `preventDefault()`, pause, save, calm overlay, restore path, and a reload that preserves the save via `sessionStorage` (`main.js:355-429`).

**Cache-busting discipline holds.** All 32 non-three imports in `main.js` carry `?v=20260926a`, and the bump procedure is documented in both `index.html` and `AGENTS.md`. I verified zero stragglers. The Windows encoding hazard is documented with a byte-safe Node workaround.

**The visual identity is doing its job.** Procedural 256 px textures with height-derived normals, a toon-graded cat with a real rig, wind-swayed bamboo in the vertex shader, 420 phase-offset stars, layered clouds, five weather states, koi with generated patterns, a shoji-door interior transition. For "no heavy downloads," this is an enormous amount of world.

## 7. Content and systems

**Quests are sound but shallow in number.** Yarn → Bokuchi (bells) → Larry (Jade Paw) is a clean three-beat chain with real gating: the Jade Paw requires the Luna leap upgrade, which requires the yarn quest, which requires understanding fences. The corral-guardian chase adds a genuine moment of tension inside a game that otherwise has none — well judged.

**The NPC routine system is the best "alive" feature.** Luna walks to the old bridge at night, Kuro appears at the river in mist and under the tea house eave in rain, Mochi plays in wind. This is exactly the Ghibli-adjacent feel the project is reaching for, and it costs almost nothing.

**Progression is well-tuned for the genre.** Five ranks, thresholds at 0/30/80/150/250, and — importantly — sprint is available from the first step (`player.js:46`, `progression.js:9-11`). Movement is never gated behind a number. The rank-4 golden bell is a real, visible reward. This is the right call and it directly serves the no-fail brief.

**But the map is one valley.** The `BUILD_GUIDE` explicitly says "don't expand the map early; deepen Kyoto first," and that instruction is being followed. The result is that a 20–30 minute player exhausts the content. The torii-top beat (`main.js:1117-1123`) — "I can see beyond this valley, I wonder what's out there?" — is a good seed, but it gates on rank ≥ 4 and is a single toast. There is no ending. `FUTURE_QUESTS.md` (47 KB) suggests the depth is planned; none of it is built.

## 8. Code quality

**Consistently good.** Hoisted scratch vectors where it matters (`player.js:7-16`, `scent.js:3-17`), documented trade-offs, `try/catch` around every storage access, no obvious leaks in the paths I traced. The `// ← see the 2026-09-11 review §1.2.2` comment in `scent.js` shows the team actually reads its own reviews and acts on them.

**Concentration risk.** `countryside.js` is 153 KB / ~3,300 lines and is imported by everything. `main.js` is 73 KB and owns the loop, menu wiring, journal, photo mode, compass, persistence *and* the quality governor. These two files are where the next regression will be hardest to place.

**Minor issues found in passing:**

- `main.js:74` and `main.js:1731` both assign `window.game`. Harmless but duplicated.
- `ui.setMode('mobile')` writes a debug string to a user-facing HUD line (§3.2).
- `refreshJournal` interpolates `n.name` and journal `text` into `innerHTML` without escaping (`main.js:1405-1418`). All current values are hard-coded strings so there is no live XSS, but it is one `discover()` call away from being one. Escape it.
- `#toast` in `index.html:159` is dead CSS — the UI uses `#toast-stack`.

## 10. Bottom line

Michi-Neko has a **better rendering and performance architecture than most teams manage in a year**, and a **save system better than many shipped games**. The world it renders is dense, characterful, and genuinely calm, and the design guardrails — no fail states, no timers, no combat, no heavy downloads — have been held with real discipline.

What it does not yet have is a **finished mobile first run**. The three bugs in §1 are the whole story: quality gets demoted on first launch and never recovers, every tap re-runs a full scene rebuild, and the two systems responsible for keeping the frame rate smooth go blind at the exact moment they are needed. Those are not architectural problems. They are three focused fixes.

The load path (§2) is the second half of that story — ~1.7 MB of unminified JavaScript over a third-party CDN, with no offline story and a boot image that weighs more than most of the game's textures combined.

Fix §1, fix §2, then **measure on real hardware** before optimising anything else. I would expect the game to be in genuinely good shape on a modern phone once those are done — the rendering foundation is already there.
